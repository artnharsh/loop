# Master Development Instructions

Set up and develop this repository as a **clean, portable, AI-friendly software project**.

I am currently using Antigravity, but I may later switch to Claude Code, Codex, Cursor, Windsurf, VS Code, or another AI coding environment.

Therefore:

> **The repository itself must always be the source of truth.**

The project must NEVER depend on Antigravity conversation history, AI memory, IDE state, or proprietary context features to understand or continue development.

Another AI with ZERO access to our previous conversations should be able to clone/open this repository, understand the project, and continue development safely.

---

# 1. Core Principle

Follow this priority:

**Correctness → Reliability → Simplicity → Maintainability → UI polish**

Do NOT over-engineer.

Prefer:

* simple architecture
* standard technologies
* minimal dependencies
* small focused files
* descriptive names
* testable business logic
* explicit behaviour
* documented architectural decisions

Avoid:

* unnecessary abstractions
* unnecessary design patterns
* unnecessary dependencies
* huge files
* duplicate logic
* vendor lock-in
* AI-generated complexity
* rewriting working code without a reason

Always make the **smallest coherent change** required to solve a problem.

---

# 2. Repository Must Be AI-IDE Independent

Never make important project knowledge available only through:

* Antigravity memory
* Antigravity rules
* Claude memory
* `.cursor`

* MCP configuration
* previous AI conversations
* proprietary AI features

IDE-specific files may exist when useful, but they must only supplement the repository documentation.

# 6. Context Resolution

When modifying a file, conceptually read context from:

**Global → Module → Code → Tests**

For example, when modifying:

```text
timer/StrictTimerManager.kt
```

consider:

1. `/AGENTS.md`
2. relevant `/docs` information
3. nearest applicable `timer/AGENTS.md`
4. relevant source files
5. relevant tests

The nearest folder context provides specialized instructions.

Root-level project invariants always remain applicable.

Folder instructions must never silently override fundamental project rules.

# 17. Development Workflow

For every non-trivial task:

### Step 1 — Understand

Read:

* root `AGENTS.md`
* applicable folder context
* relevant architecture/decisions
* relevant existing implementation

Do not start coding before understanding the existing system.

### Step 2 — Plan

Briefly determine:

* files affected
* behaviour changing
* potential risks
* tests required

Do not create enormous planning documents for small changes.

### Step 3 — Implement

Make the smallest coherent change.

Do not refactor unrelated working code.

### Step 4 — Validate

Where applicable:

* compile
* run tests
* lint
* verify expected behaviour
* inspect errors/warnings

Never claim something works simply because the generated code looks correct.

### Step 5 — Review

Review your own diff.

Look for:

* regressions
* accidental behaviour changes
* duplicated code
* unnecessary dependencies
* debug code
* security problems
* broken project invariants

### Step 6 — Update Context

Update documentation/context only where the implementation materially changed.

# 23. StrictBlock Product Invariants

For this specific project, these rules are fundamental.

The application should remain intentionally simple:

**Select apps → choose timer → confirm → apps remain blocked until deadline.**

During an ACTIVE strict session:

* NO pause
* NO stop
* NO cancel
* NO break
* NO temporary unlock
* NO emergency in-app unlock
* NO PIN bypass
* NO password bypass
* NO advertisement-based bypass
* NO removing blocked applications
* NO weakening the active block
* NO shortening the deadline

If extending a session is implemented:

```text
newDeadline >= currentDeadline
```

must always remain true.

Never add an in-app early-exit mechanism unless I explicitly request one.

The absence of an early-unlock feature is **intentional product behaviour, not missing UX**.

Do not "improve the user experience" by adding one.

---

# 24. StrictBlock Safety Invariants

The application must protect against accidental critical-app blocking.

StrictBlock itself must NEVER be blockable.

Critical Android functionality should not be blockable, including where identifiable:

* Settings
* System UI
* launcher/home
* Phone/Dialer
* emergency-related functionality
* Package Installer
* Permission Controller
* other components required for basic device operation

Prefer preventing selection when uncertain about whether blocking an application could make the phone difficult to operate.

Always show a final confirmation before starting a strict session.

---

# 25. StrictBlock Persistence

An active session must survive:

* closing StrictBlock
* process death
* reopening StrictBlock
* device reboot

Store an absolute deadline rather than relying only on an in-memory countdown.

Conceptually:

```text
lockedUntil = absoluteTimestamp
```

Blocking decisions should derive active state from persisted session information.

When:

```text
currentTime >= lockedUntil
```

the session may expire normally.

Do not silently clear a valid active session because the application UI was recreated.
